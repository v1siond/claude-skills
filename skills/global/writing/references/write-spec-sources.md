# Sources

Shared by him when he asked for a proper spec format.

- https://www.mindstudio.ai/blog/how-to-write-a-software-spec : Overview, Data model (field, type,
  required, rules, relations), Features (trigger, inputs, behaviour, output, errors), Edge cases, Auth and
  permissions as a role by action table, optional UI notes, open questions marked. "Write behaviors, not
  wishes." "Edge cases are where bugs live." Name the actor, no relative terms, two examples per rule,
  leave rationale out.
- https://rohirrim.ai/blog/the-perfect-proposal-format-design-guide/ : title block, table of contents,
  executive summary, main body (plan, deliverables, timeline), cost, conclusion; consistent headings;
  "Visual aids can make your entire proposal more digestible"; concise.
- https://www.zoom.com/en/blog/proposal-format-for-business/ : summary opens with the client's challenge
  in 3 to 5 sentences, restate the problem in the client's words, deliverables as a labelled list, one line
  of exclusions, dated milestones, scannable (white space, bullets, bold labels), no padding.
- Our own earlier spec that read well: a client repo specs/2026-07-31-parent-child-orders-design.md (the ask,
  a decisions table, what gets built).
